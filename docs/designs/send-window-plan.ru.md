# Окно Send в симуляторе телефона — план (на русском)

Это пересказ для проверки, что задача понята верно. Полный технический план с решениями, диаграммами и реестрами ошибок: `docs/designs/send-window-plan.md` (на английском, источник истины).

Статус: ревью CEO и инженерное ревью пройдены, код не написан. Учтено ваше указание использовать `POST /v2/screen` (раздел 4).

## 1. Что строим

В симуляторе телефона у токена Tron есть кнопка **Send**. Она открывает экран отправки, похожий на экран кошелька:

- поле **адрес получателя** (проверка формата Tron-адреса, включая контрольную сумму);
- поле **сумма** в токене, кнопка **Max** (для TRX Max = баланс минус комиссия);
- строка **комиссии**: живой расчёт через TronGrid, подписан как «оценка» (estimate); если сеть недоступна, показываем подписанное резервное значение;
- кнопка **Отправить**. Отправка симулируется, настоящей транзакции нет;
- пока пользователь вводит адрес, идёт **проверка риска** адреса (AML) и определяется **метка принадлежности** (например, название биржи).

Сначала только Tron. Ethereum отложен (записан в `TODOS.md`).

## 2. Как работает проверка риска

1. Введён валидный адрес. Сначала смотрим в **статический список (seed)** известных демо-адресов. Если адрес там, ответ мгновенный и без обращения к сети.
2. Если адреса в списке нет, телефон обращается к нашему **Cloudflare Worker** (отдельный маленький сервер). Worker вызывает Aegis и возвращает телефону только `{level, label?}`: уровень риска и необязательную метку. Числового скоринга, причин и флагов телефон не получает вообще.
3. Результат:

| Результат | Что видит пользователь |
|---|---|
| низкий риск | Send работает как обычно, при наличии метки показывается она |
| **высокий риск** | всплывающее окно: заголовок «We don't recommend sending to this address», строка «Based on Aegis data at the time of the check. Details aren't shown.». Без скоринга и без причин. Кнопки: **Cancel** (основная) и **Send anyway** |
| не удалось проверить | «Couldn't verify this address». Это не «безопасно» и не «опасно». Send разрешён |
| проверка ещё идёт | Send удерживается до 15 секунд, потом считаем проверку недоступной |

Текст попапа утверждён вами (решение D12). «Не рекомендуем, причины не раскрываем» выполнено буквально.

## 3. Где живёт ключ Aegis и как его не «слить» (безопасность)

**Короткий ответ: ключ живёт только как секрет Cloudflare Worker. Ни в браузере, ни в репозитории, ни в GitHub Secrets его нет.**

Почему не GitHub Secrets. Сайт статический (GitHub Pages). Всё, что попадает в сборку, публично: любой видит файлы в браузере. GitHub Secrets умеют только подставлять значения во время сборки, то есть ключ всё равно оказался бы внутри публичных файлов. Поэтому от идеи «ключ в GitHub Secrets» пришлось отказаться, это главный вывод первого ревью.

Что делаем вместо этого:

- **Где лежит:** секрет `AEGIS_API_KEY` в Cloudflare Worker. Задаётся командой `wrangler secret put AEGIS_API_KEY` с вашего компьютера. Прочитать его обратно нельзя.
- **Что видит браузер:** только адрес Worker (публичная переменная репозитория `VITE_RISK_PROXY_URL`). Секрета там нет.
- **Локальная разработка:** ключ в файле `worker/.dev.vars`, он добавляется в `.gitignore`. Файл `.env` с ключом не используется.
- **Отдельный ключ для демо:** создать в личном кабинете Aegis отдельный ключ с **месячным лимитом**. Это жёсткая страховка: даже если всё остальное сломается, потратить можно только лимит.
- **Защита от злоупотребления** (Worker):
  - принимает запросы только с нашего сайта (точное совпадение origin; это не защита от скриптов, а отсечение случайных использований);
  - проверяет формат адреса и сети до обращения к Aegis;
  - лимит запросов на посетителя и общий **дневной бюджет**. Счётчики ведёт Durable Object, потому что обычный KV не атомарен и под нагрузкой пропустит лишнее;
  - кэш результатов (повторный адрес не стоит денег);
  - **выключатель** `RISK_ENABLED`: одной переменной отключается живая проверка, сайт продолжает работать на seed;
  - если хранилище счётчиков недоступно, Worker закрывается (не отвечает), а не пропускает всё подряд;
  - ответ ограничен ровно двумя полями, метка очищается от лишнего.
- **Защита от случайной утечки:** после сборки скрипт ищет в `dist/` текст, похожий на ключ (`aeg_…`), и **роняет деплой**, если нашёл.
- **Ротация:** новый ключ командой `wrangler secret put`, старый отзывается в кабинете Aegis.
- **Деплой Worker** пока ручной (`wrangler deploy`), по инструкции в `CONTRIBUTING.md`. Автодеплой из CI вынесен в TODO, и только тогда понадобится GitHub Secret с токеном Cloudflare (не с ключом Aegis).

Честное ограничение: Worker публичный, поэтому полностью запретить чужие запросы нельзя. Мы ограничиваем **ущерб** (лимиты, бюджет, кэш, месячный потолок ключа и выключатель). Для демо этого достаточно. Капчу (Turnstile) сознательно не добавляли (решение D8).

## 4. API Aegis: `POST /v2/screen` (учтено по вашей ссылке)

Раньше в плане стоял `POST /v2/inspect-address`: он асинхронный, отвечает 202 и требует опрашивать результат 5–30 секунд, поэтому я придумал схему «телефон опрашивает через Worker». Вы указали `/v2/screen`, и она проще:

- **синхронная**: ответ в том же запросе, в примере из документации около 60 мс;
- заголовок `Authorization: Bearer aeg_…`, тело `{address, network}`, сеть `TRON` поддерживается (также `ETH`, `BSC`);
- цена **0.1 кредита** за вызов (ранее прикидывал около 2, это было неверно);
- заголовок `Idempotency-Key`: повтор того же запроса в течение 24 часов возвращает кэш **бесплатно**. Ключом идемпотентности будет хэш от «сеть + адрес + день»;
- в ответе есть `verdict.risk_level` (`none`, `low`, `medium`, `high`, `critical`, `sanctioned`), `verdict.risk_score`, `verdict.label` (может быть `null`) и `coverage.data_available`.

Как Worker превращает ответ в наши три уровня:

| Ответ Aegis | Наш уровень |
|---|---|
| `high`, `critical`, `sanctioned` | высокий (попап) |
| `medium` | осторожно |
| `low` | низкий |
| `none` и `data_available: true` | низкий |
| `none` и `data_available: false` | **неизвестно**, не «безопасно» (в документации прямо сказано, что `none` не значит «чисто») |

Что изменилось в плане: схема с опросом, дескрипторами и вторым маршрутом отменена (решение E2 заменено). Остаётся один маршрут `POST /check` на Worker. Не изменилось: seed, лимиты, счётчик на Durable Object, формат ответа `{level, label?}`.

Нужно уточнить у Aegis: лимиты частоты запросов (в документации их нет) и доступен ли вашему ключу endpoint `/v2/screen`. Учтите, что `/v2/screen` проверяет только санкции и консенсус источников и не анализирует граф связей. Для полной проверки есть `/v2/check-address`.

## 5. Комиссия Tron (проверено живым запросом)

Использую бесплатный TronGrid без ключа. Живой пробный запрос на USDT:

- перевод на адрес, который уже держит токен: **64 285 energy**;
- перевод на «пустой» адрес: **130 285 energy** (в два раза больше);
- симуляция от отправителя без USDT падает с ошибкой, оценки нет.

Поэтому для оценки нужен «эталонный» отправитель с токеном либо константы 65k/130k, а подпись всегда «оценка». Для нативного TRX добавляется 1 TRX, если получатель не активирован.

## 10. Стоимость (добавлено 2026-10-13)

- **Cloudflare Worker, бесплатный план:** 100 000 запросов в день, 10 мс процессорного времени на запрос. KV: 100 000 чтений и 1 000 записей в день. Durable Objects доступны и на бесплатном плане, но только с хранилищем SQLite (в `wrangler.toml` класс объявляется как `new_sqlite_classes`). Для 1000 запросов в месяц это с огромным запасом: платить Cloudflare не нужно. Платный план стоит от $5 в месяц и понадобится, только если вырастете на несколько порядков.
- **Основные деньги уходят в Aegis:** 0.1 кредита за вызов, 1 кредит равен 1 USDT. Тысяча живых проверок в месяц дают до 100 USDT. Повторы одного адреса в течение суток бесплатны (Idempotency-Key), seed для демо-адресов не тратит ничего. Поэтому на ключе нужен месячный лимит, а дневной бюджет Worker стоит задать около 30 проверок в день.

## 11. Дизайн экрана Send (результат /plan-design-review, 2026-10-13)

Оценка полноты дизайна выросла с 3/10 до 8/10. Принято 14 решений (в английском плане DR1–DR14):

- **Порядок на экране (DR1):** адрес (полностью, в одну строку, моноширинный), под ним строка статуса проверки с меткой и подписью «Address is checked by Aegis», затем сумма, тихая строка комиссии, кнопка Send внизу.
- **Попап (DR2, DR8, DR10):** статус «Caution» виден сразу под адресом, а попап открывается только по нажатию Send, не при вставке адреса. Cancel оставляет адрес и сумму, фокус возвращается в поле адреса. Send anyway идёт сразу в отправку. Попап рисуется внутри рамки телефона, в двух видах: iOS-alert и Android-диалог.
- **Формулировки (DR3, DR4, DR7):** при низком риске пишем нейтрально «No risk signals found», а не «Safe» (Aegis сам говорит, что `none` не значит «чисто»). Зелёная отметка только если Aegis вернул метку владельца. При сбое: «Couldn't verify this address. Check again». Индикатор проверки появляется через 250 мс, надпись на кнопке не меняется.
- **Сумма и комиссия (DR5):** тексты для пустой суммы, нуля, суммы больше баланса и нехватки TRX на комиссию. Комиссия около 6.4 TRX для USDT на обычный адрес и около 13 TRX на пустой (в моих первых макетах стояло 13.2: это была ошибка в два раза, исправлено).
- **Отправка (DR6):** короткий экран «Sent (simulated)» с пометкой «Simulated — no transaction was sent» и кнопкой Done. Полные квитанции по-прежнему не делаем.
- **Цвета (DR9):** цвета предупреждения и ошибки из `style.css` не проходят контраст на светлом экране телефона (2.15:1 и 3.75:1 вместо 4.5:1), поэтому у экрана Send свои цвета для светлой и тёмной темы, все проверены расчётом.
- **Доступность (DR11):** цели касания не меньше 44 px, порядок Tab, в попапе фокус сначала на Cancel и Esc отменяет, статус озвучивается один раз за вердикт, отключение анимаций при `prefers-reduced-motion`.
- **Остальное (DR12–DR14):** если Send недоступен (не Tron-токен или нет WebCrypto), показываем плашку внутри телефона вместо `alert()`. Адрес из seed выглядит так же, как адрес с живой проверкой. «Назад» работает без подтверждения.

Визуальных макетов от gstack designer нет (нужен OpenAI API-ключ, его нет). Реализованный экран нужно будет проверить через `/design-review`. Отдельный DESIGN.md записан в TODO (P3).

## 12. Повторное инженерное ревью (2026-10-13) — что изменилось

После перехода на `/v2/screen`, деплоя Worker из Git и дизайн-решений принято 6 решений:

- **Выключатель (E5):** `RISK_ENABLED` теперь секрет Worker, а не переменная в `wrangler.toml`: Cloudflare перезаписывает переменные панели при каждом деплое из Git, секреты остаются. Нет значения (или не `"true"`) значит живые проверки выключены, сайт работает на заготовленном списке.
- **Средний риск (E6):** `medium`, `high`, `critical` и `sanctioned` показываются как «осторожно» (янтарная строка, попап по Send). `low` и `none` с данными — чисто, `none` без данных — «не удалось проверить».
- **Метка владельца (E7):** Worker отдаёт метку только для «чисто». Для рискованного адреса ответ ровно `{level}`: имя владельца часто само объясняет причину, а вы просили причин не раскрывать.
- **Тесты перед деплоем Worker (E8):** сборка Cloudflare запускает тесты репозитория (root `worker`, build command вида `cd .. && npm ci && npm test`, watch paths `worker/**` и `tests/**`). Падающий тест оставляет прошлую версию Worker живой. Точные настройки проверяются при первой сборке.
- **Один валидатор адреса (E9):** `src/send/tron-address.ts` используют и клиент, и Worker (иначе Worker оплачивал бы заведомо неверные адреса).
- **Регрессии (E10):** до правки `phone-frame.ts` пишем тесты на уже работающее поведение: клик по обычному действию (текст алерта) и навигацию список → карточка → назад.

Выключен лишний файл `src/send/net.ts` (хватает встроенного `AbortSignal.timeout`). Устаревший TODO «автодеплой Worker в CI» удалён: деплой теперь из Git Cloudflare (ваш выбор).

Состояние: план согласован целиком (CEO, инженерное ревью, дизайн), нерешённых вопросов нет. Внешнего обзора нет (Codex не установлен). Готово к реализации по трём PR: фундамент, экран Send на seed, живая проверка через Worker.

# CEO Plan: Token UI Studio & Multi-Chain Registry

## 11-Section Deep Review — Accepted Findings

Batched per-section per user preference. Each item below is now part of the
plan's scope (except where noted as declined/deferred).

**Section 1 (Architecture):**
- Registry repo must require PR + passing status checks before merge to the
  default branch — otherwise the CI schema-gate is advisory, not enforced.
- Bundled default registry + presets must work fully offline/without any
  GitHub API call, so a GitHub outage doesn't brick the tool.
- Widget/action rendering should use a `type → handler` lookup table, not
  if/else branching (implementation guidance for Next Steps #2).
- Deferred to TODOS.md: embeddable `<token-card>` web component, decoupled
  from the Studio UI, so real wallets could import the renderer directly.

**Section 2 (Error/Rescue):**
- Rate-limit hit with cold cache → show "Rate-limited by GitHub — try again
  in N minutes." **Superseded by Outside Voice T3 below: no PAT option.**
- Malformed/unparseable registry JSON → show "This registry has invalid
  JSON at {path} — contact the registry maintainer," not a crash/blank UI.
- External icon URL fails to load (404/timeout) → fall back to a generic
  placeholder glyph, same degraded path as a domain-rejected icon.

**Section 3 (Security):** — two High-impact findings directly on this
project's own phishing thesis.
- Shared preview links render with an unmistakable "PREVIEW ONLY — not from
  a verified registry" banner; the demo-alert always shows the full literal
  target URL, never just an icon/label.
- Viewing any non-default registry (multi-registry client) prominently shows
  "Viewing: {owner}/{repo}" so an arbitrary/typosquatted repo can't be
  mistaken for the canonical one.
- **Superseded by Outside Voice T3:** the PAT-paste option is dropped
  entirely (see below) rather than mitigated — a static site asking users
  to hand it a bearer token contradicted the project's own "no ad hoc
  trust-me security mechanisms" thesis.

**Section 4 (Data/Edge Cases):**
- Guard against stale-fetch races: tag fetches with a request ID/
  AbortController, ignore responses superseded by a newer selection.
- Disable the Deploy/Propose button immediately on click until the flow
  completes — no duplicate tabs/downloads from rapid clicks.
- Reject pasted JSON above ~100KB with a friendly message before validating.
- Confirm before discarding unsaved edits when switching preset/token/network.

**Section 5 (Code Quality):**
- Client-side validator bundle and the CI Action's validator must build from
  one canonical `registry.schema.json` — never two independently maintained
  copies of the validation rules.
- Runtime-validate (ajv) every fetched config BEFORE treating it as a typed
  `TokenConfig` — no `as TokenConfig` cast on unvalidated external JSON.

**Section 6 (Tests):**
- Explicit test strategy added to Next Steps: unit tests for validators/
  renderers/URL builders, an integration test for the fetch→validate→render
  pipeline, 1-2 E2E smoke tests.
- All GitHub API calls mocked/stubbed in tests — no test may hit the real
  API (avoids CI flakiness from rate limits/network).
- Shared adversarial fixture corpus (homograph domain, unknown types,
  oversized icon, schema-version mismatch) used by both client-side and
  CI-side tests.

**Section 7 (Performance):**
- Virtualize the sidebar token list above ~200 tokens.
- (Declined this round: debounced editor validation, per-session config
  caching — reasonable v1 simplifications, not required.)

**Section 8 (Observability):**
- Structured console warnings for every degraded/rejected path (unknown
  widget type, rejected icon domain, rate-limited API, etc.) so a reported
  bug is reconstructable from a console screenshot alone.
- A permanently-known-bad fixture config that the CI schema validator must
  always reject — a canary confirming the CI gate hasn't silently broken.

**Section 9 (Deployment):** — response was "no preference" (unresolved,
see Unresolved Decisions in the Completion Summary below), covering:
build+publish-to-Pages triggering only on default-branch merges, PR preview
deploys for reviewers, and an automated post-deploy smoke check.

**Section 10 (Long-Term Trajectory):**
- Add a CONTRIBUTING.md documenting the schema, the PR/review flow, and how
  to add a token, as an explicit v1 deliverable.
- (Declined: Phase 2 standalone `@token-ui/schema` npm package — not added
  to TODOS.md per user choice.)

**Section 11 (Design/UX):**
- Broken/truncated share-link fragment shows "This preview link appears
  broken or truncated" instead of a blank/crashed state.
- (Declined this round: explicit desktop-first statement, accessibility of
  the Studio's own UI chrome — not added.)

- **Auditability erosion.** Approach A→B's original selling point was
  "boring, one-sitting-reviewable." CompressionStream, sessionStorage

  but worth remembering when tempted to add a 6th expansion later.

**Resolved tensions:**

**T1 — Scope calibration (tz.md offered a single-file deliverable; this plan
built for hypothetical external adopters with no evidence of demand).**
Resolution: **Keep the accepted scope.** Each item was approved individually
and deliberately in Step 0 with clear reasoning (turn the schema into a real
open standard) — not re-litigated.

**T2 — No reviewer actually named for the "PR-gated review" security thesis.**
Resolution: **Add a CODEOWNERS file + review policy.** At least one named
maintainer's approval is required on every token-config PR, alongside CI
passing — added to Next Steps below.

**T3 — PAT-paste option contradicts the project's own "no ad hoc trust-me

Resolution: **Drop the PAT option entirely.** On rate-limit, show only a

Resolution: **Document as an inherent limitation, not a fix.** The

coordinated fake website + action URL — the real defense is the human PR
reviewer (see CODEOWNERS above), not this heuristic."

## Vision

### 10x Check
The version that's 10x more valuable for ~2x the effort turns the Studio from
"an app for our one registry" into a generic client for the open schema —
any project can point it at their own GitHub repo following the same
`registry.schema.json` convention. Combined with a live trust/security score
(contrast checks, phishing-pattern detection on action URLs) shown in the
editor before submission, it stops being just an authoring tool and becomes
a design tool for trust: you know your card is safe before you ever open a PR.

### Platonic Ideal
An issuer opens the Studio, picks a network, and within 2 minutes has a card
that already tells them whether it'll pass review, previews correctly on both
iOS- and Android-style wallet chrome, and one click prepares a real PR —
against the canonical registry or their own fork. The schema itself becomes
popular enough that other wallets consume it independently of this UI, the
way Uniswap's token-lists schema outgrew Uniswap.

### Item 1 detail — phishing-pattern heuristic set (static, no backend calls)
Client-side, deterministic checks only (no external threat-intel API — that
would violate the "no backend" constraint):
- Punycode/IDN homograph detection on any domain used in `external_url`/
  `deeplink` action URLs (flag non-ASCII-lookalike domains).
- Domain allowlist warning: flag (not block) any action URL whose domain
  differs from the token's declared `website`/`explorer` domain — a mismatch
  is a signal for the human reviewer, not an automatic rejection.
- WCAG AA contrast ratio check: `badgeText` color vs. `theme.primaryColor`,
  and vs. the *nearest* gradient stop in `background.colors` (the color
  stop closest to the badge's on-screen position, since gradients have
  multiple stops).
- Widget-count sanity: flag (not block) more than 4 widgets on one card as
  likely UX clutter.
All checks are advisory (shown as a score/warning list in the editor) — none
of them block CI merge; CI still only enforces schema validity (per the
design doc). This keeps the "no backend" constraint intact.

### Item 2 detail — rate-limit and schema-version guardrails
- Cache the target registry's `default_branch` and file-listing response
  client-side per session (sessionStorage) to avoid repeat calls against
  GitHub's unauthenticated 60 req/hr/IP limit; on a 403/rate-limit response,
  show a clear "rate-limited by GitHub — try again in N minutes" message
  rather than failing silently. **No PAT-paste option** (see Outside Voice
  T3) — living with the 60/hr ceiling is the correct tradeoff for a static,
  no-backend tool.
- Every registry the Studio points at must declare a `schemaVersion` field
  at its root (extending the schema locked in the design doc's Next Steps
  #1). The Studio refuses to render/edit a registry whose `schemaVersion` it
  doesn't recognize, rather than guessing — this is the versioning handling
  the design doc's single-registry assumption never had to consider.

### Item 3 detail — fragment payload encoding
Config is JSON-stringified, then compressed using the browser-native
`CompressionStream('deflate')` API (falling back to uncompressed
base64url if unsupported — no hand-rolled compression code, per this
project's own "boring, auditable, minimal surface" philosophy) and
base64url-encoded into the URL fragment
(`#c=<encoded>`). If the encoded payload exceeds a practical URL length
threshold (~2000 characters, the conservative cross-browser limit),
fall back to a plain "copy JSON to clipboard" action instead of a link —
mirroring the same size-fallback pattern already used for the GitHub
PR-prep flow in the design doc.

### Item 5 detail — template gallery, v1 scope
v1 gallery ships with a small number of additional hand-authored templates
(e.g. meme coin, LP token — alongside the original USDT Yield / TWT
Governance / RWA Bond three) so the total is not open-ended. Importing real
tokens from a public list (tokenlists.org) remains a distinct, deferred v2
idea gated on the multi-registry client (item 2) proving out first — it is
not folded into v1's accepted scope.

## Accepted Scope (added to this plan)
- Live trust/security score panel in the editor — static heuristics only
  (contrast, homograph/domain-mismatch detection, widget-count sanity), all
  advisory and shown before PR submission; CI enforcement stays schema-only.
- Studio is a generic client for any GitHub repo implementing
  `registry.schema.json` (registry URL is configurable, not hardcoded),
  with client-side rate-limit caching and a `schemaVersion` compatibility
  gate.
- Shareable read-only preview link via a compressed, base64url-encoded URL
  fragment, with a clipboard-copy fallback above ~2000 characters.
- Dual wallet-chrome (iOS/Android) + light/dark toggle on the live simulator.
- Preset/template gallery: a small fixed set of additional hand-authored
  templates beyond the original 3 presets (not an open-ended import).

## Deferred to TODOS.md
- Diff-against-production view for edits to existing token configs.
- v2: import real tokens from a public list (e.g. stablecoin.cmc.eth via
  tokenlists.org) as additional seed data, gated on the multi-registry
  client (item 2) proving out first.
- Fallback path for GitHub API `default_branch` lookup failure in the
  Deploy/Propose flow (flagged as a Reviewer Concern in the design doc —
  now partially addressed by item 2's session-cache + rate-limit messaging,
  but still needs resolving during implementation, not deferred indefinitely).
